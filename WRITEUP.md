# Write-up

## Schema reasoning
The relationship chain `organizations → org_members → workflows → workflow_steps / workflow_triggers`, and `workflows → workflow_runs → step_runs`, maps directly onto the two things every permission check needs: *which org does this row belong to* and *what is the caller's role in that org*. Keeping `org_id` denormalized onto `workflow_runs` (in addition to reachable via `workflow_id`) was a deliberate trade — it lets both Hasura permissions and the engine's SQL filter on org directly with one join instead of two, which matters once cross-org isolation is being checked on every single query. `step_runs` carries `approved_by`/`approved_at` directly rather than a separate approvals table, since an approval is 1:1 with the paused step run and doesn't need its own lifecycle. `workflow_steps.on_true_step_id` / `on_false_step_id` model `conditional_branch` as an explicit graph edge rather than an implicit "next row in step_order," so a branch can skip steps or jump backward without special-casing the engine's loop.

## Two permission layers
**Layer 1 (org + role scoping)** lives entirely in Hasura's declarative permissions. Every table's permission filter traverses `organization → org_members` and checks `user_id = X-Hasura-User-Id`, so scoping isn't a separate check bolted onto a role check — the two are the same expression. Because a user's role differs per org, all authenticated users share a single Hasura role (`user`); RBAC comes from evaluating `role: {_in: [...]}` on the *joined* `org_members` row, not from Hasura's static role system. That's what makes "editor in Org A" structurally unable to touch Org B's rows even while holding the same role: the row-level filter re-derives the caller's membership from scratch on every request, scoped to the row's own org, so there's no shared "am I an editor" flag that could leak across orgs.

**Layer 2 (step-level gating)** has two flavors. Restrictions on *creating* certain rows (a `db_write`/`notify` step, a `webhook` trigger) are still expressible as Hasura permission checks — they're just column-value-dependent versions of the same relationship check, requiring `role = owner` only when `type` is one of the sandbox-escaping values. But *resuming a paused run* isn't a row a client can insert or update at all — `workflow_runs`/`step_runs` have no client-facing insert/update permissions, full stop. The only way to move a paused run forward is the `approveStep` Action, so the approver-role check necessarily happens in the Node handler (`functions/src/server.js`), which re-derives the caller's org role the same way Hasura would, then does the state transition and resumes execution in one server-side operation. This was necessary rather than a stylistic choice: a database permission can gate a row's shape, but it can't decide "resume execution from here," since that's a side effect, not a write.

## Approval-gate pause/resume
`executeRun()` runs steps in `step_order` (or via `on_true/false_step_id` jumps), writing a `step_runs` row before and after each step so the subscription reflects progress live. Hitting an `approval_gate` step short-circuits the loop: the step run and the parent run are both marked `paused`, and the function returns without advancing. `approveStep` re-validates the step is actually `paused`, checks the approver's role, stamps `approved_by`/`approved_at`, and calls `executeRun` again with `resumeFromStepId` set to the just-approved step — the loop finds that step's index and continues from `idx + 1`, reusing the same retry/branch logic as a fresh run. Because the engine reads `workflow_steps` fresh each call rather than holding run state in memory, pause and resume can happen in two entirely separate HTTP requests (even minutes/hours apart) with no in-process state to lose.
